Nod v1.2.0 is a security release. It closes the gaps found in the 1.1.0
security assessment — what a device signs, who can verify it, and how device
credentials travel — collapses the request-digest numbering so each digest
pairs with its decision payload, and ships the Nod mascot icon refresh that was
prepared as 1.1.1 but never published. Signed decision bytes recorded by 1.1.x
remain verifiable; the server, relay and every client must be upgraded
together.

## Upgrade together

- **1.1.x clients stop working against a 1.2.0 server.** The sync WebSocket
  takes the device token only from the `Authorization` header of the upgrade
  request; the `?token=` query form is gone, so an older client gets `401`
  before the upgrade. Update the macOS, iOS, Windows and TUI clients in the
  same window as the server. Enrollment, keys and history are preserved: no
  re-enrollment is needed.
- **Enrollment requires a signing key.** `POST /api/v1/enroll` without
  `signing_key` returns `400` and leaves the code unused. A device row that has
  no key cannot decide; every recorded device decision carries a verified
  signature, so `"signature": null` on a decision view is a verification
  failure, never a weaker approval.
- **No approve or reject from notifications, on any platform.** iOS and macOS
  pushes and local alerts offer a single Open Nod action, Windows toasts carry
  no buttons, and the desktop app only answers from its foreground window.
  Every answer is signed over the digest of the card the user actually saw.

## What's changed

- **Sign what the user saw.** Every submit — ordinary or value card, every
  client — passes the digest of the rendered request, and the shared signing
  path refuses to sign a copy whose digest differs ("Request changed. Review
  it again before answering."). A server that shows one request and serves
  another at submit time no longer obtains a signature.
- **Verify without trusting the server.** The admin device list, the
  enrollment response and `/api/v1/users/me/devices` expose each device's
  `signing_key_id` and `signing_public_key` so issuers can pin them out of
  band. `nod-verify`, shipped next to `nod-server` for every target, takes the
  create response, the decision and the pinned keys and recomputes the digest,
  rebuilds the canonical payload and checks the P-256 signature offline,
  ignoring the `public_key` and `verified` the server attached. Rust issuers
  can call `nod_proto::verify_decision_receipt` directly. The agent skills now
  say: act only on exit 0.
- **Device token off the wire path.** The sync socket authenticates with the
  `Authorization` header only, so the long-lived device credential never lands
  in proxy, access or browser-history logs.
- **Server hardening.** The admin session cookie is `Secure` when the login
  arrives over TLS (directly or via `X-Forwarded-Proto`), failed admin logins
  are delayed, and a short admin token logs a startup warning. Enrollment codes
  are sampled uniformly from the 36-symbol alphabet. `image_url` and every
  `links[].url` must be absolute http(s) URLs, and control characters are
  rejected in `image_url` and `dedupe_key`. The data and audit directories are
  created `0700` and the audit file `0600` on Unix.
- **Collapsed request digests.** Ordinary cards now issue `nod-request-v1`
  (the structured encoder over the immutable content plus the salted
  `recipients_commitment`) paired with `nod-decision-v1`; value cards issue
  `nod-request-v2` (the canonical value encoder) paired with `nod-decision-v2`.
  The old line-snapshot `nod-request-v1`, the structured `nod-request-v2` and
  the value `nod-request-v3` encoders are kept as verification-only functions.
  See [docs/signing.md](https://github.com/batteryshark/nod/blob/v1.2.0/docs/signing.md).
- **Nod mascot everywhere.** The iOS, macOS and desktop apps use the mascot app
  icon, regenerated at every catalog size from one 1024 px master, and the
  macOS menu-bar item and desktop tray use the mascot line-art glyph as a
  template image so it tints correctly on light and dark bars. The bundled web
  and README icons come from the same master.

## Compatibility of already-issued cards

Cards and decisions written by 1.1.x keep verifying. The server accepts a
decision whose `request_digest` matches *any* known encoder for that card's
content, so a device still answering a card it received under the old
`nod-request-v2` (ordinary) or `nod-request-v3` (value) tag signs with that
tag's encoder and is accepted. Clients select the encoder from the tag they
received: a context with `recipients_commitment` is never the line snapshot,
and a card is the value variant exactly when it carries an `answer_field`.
`nod-verify` applies the same rule to the create response and reports which
encoder matched (`digest_encoder`: `structured`, `value`, or `legacy-*`). The
top-level `request.request_digest` of full and single-recipient views stays
for backward compatibility as the frozen line-snapshot value.

## Upgrade and distribution

Upgrade the server and standalone APNs relay first, then every client. Pin
device keys from the admin page's Devices table before relying on
`nod-verify`; keys are fixed at enrollment and do not rotate. Review
[docs/deploy.md](https://github.com/batteryshark/nod/blob/v1.2.0/docs/deploy.md)
for the verifier walkthrough and the reverse-proxy note on the WebSocket
`Authorization` header.

The public macOS distribution route remains a Developer ID-signed, notarized
and stapled DMG; Windows remains an unsigned desktop ZIP. iOS direct-install
handoff is separate from the public macOS release; see the
[Apple deployment guide](https://github.com/batteryshark/nod/blob/v1.2.0/client/nod-apple/docs/APPLE.md).
